# 项目难点及实现方式

> 文档日期：2026-05-14  
> 适用项目：`D:\study\system\low-carbon-dormitory`  
> 使用场景：课程答辩、项目汇报、技术说明

## 1. 难点一：低碳积分规则如何抽象

### 1.1 难点说明

本项目不是简单展示宿舍水电数据，而是要把原始的水电消费数据转化为低碳评价结果，包括积分、排名、荣誉和可视化指标。  
难点在于，水电数据本身只是原始业务数据，不能直接作为低碳评价结果，必须先抽象成可计算的规则模型。

### 1.2 实现方式

项目将低碳积分逻辑从页面中抽离，统一放在后端规则服务中处理：

- 规则管理服务：`low-carbon-dormitory-spring/src/main/java/com/example/lowcarbondormitory/service/rule/LowCarbonRuleService.java`
- 管理端规则接口：
  - `GET /admin/low-carbon-rules`
  - `PUT /admin/low-carbon-rules`
  - `POST /admin/low-carbon-rules/preview`
- 学生端只读规则接口：
  - `GET /student/low-carbon-rules`

实现思路是：

1. 将评分规则和荣誉规则作为独立配置对象管理。
2. 管理员可以动态查询、修改和预览规则效果。
3. 后端根据当前规则计算低碳分值，而不是前端写死公式。
4. 页面只负责展示结果，不直接承担计算逻辑。

### 1.3 答辩可用表述

本项目将低碳积分从“写死在页面中的逻辑”抽象成“后端统一管理的可配置规则”，这样既提高了系统灵活性，也降低了后期规则变更的维护成本。

## 2. 难点二：多模块数据联动如何实现

### 2.1 难点说明

项目中宿舍水电、账单流水、低碳积分、奖励兑换、管理员配置并不是独立存在的，而是互相关联的。  
例如，水电消费会影响低碳积分，低碳积分又会影响奖励兑换，因此模块之间存在较强的数据耦合关系。

### 2.2 实现方式

项目采用“实体拆分 + Service 聚合”的方式实现多模块联动。

核心实体包括：

- `StudentBase`
- `StudentExt`
- `DormInfo`
- `DormFee`
- `DormFeeHistory`
- `UtilityRateConfig`
- `LowCarbonScoreRule`
- `LowCarbonHonorRule`
- `RewardItem`
- `RewardExchangeRecord`

这些实体位于：

- `low-carbon-dormitory-spring/src/main/java/com/example/lowcarbondormitory/entity/`

在业务层，由专门的服务类统一做聚合处理，例如：

- 宿舍低碳看板服务：`service/dashboard/LowCarbonDashboardService.java`
- 学生个人低碳看板服务：`service/student/StudentPersonalLowCarbonDashboardService.java`
- 奖励服务：`service/student/RewardService.java`

具体实现思路是：

1. 先将不同业务拆成独立实体和独立表。
2. 再由 Service 层根据业务场景读取多个模块的数据。
3. 最后在后端统一组装成前端需要的响应对象。

### 2.3 答辩可用表述

面对多模块联动问题，我没有把逻辑直接写在控制器或页面中，而是通过独立实体管理底层数据，通过 Service 层统一完成跨模块聚合，降低了耦合度。

## 3. 难点三：事务一致性如何保证

### 3.1 难点说明

项目中有多类操作具有明显事务特征，例如：

- 学生充值
- 管理员扣费
- 奖励兑换

这些操作不是只更新一张表，而是要同时修改余额、流水、积分、库存和记录。  
如果处理不好，就可能出现“余额变了但流水没记”“库存扣了但兑换记录没写”的不一致问题。

### 3.2 实现方式

项目将这类高一致性业务集中放在后端 Service 层中处理。

相关服务包括：

- 支付与账务服务：`service/student/StudentPaymentService.java`
- 奖励兑换服务：`service/student/RewardService.java`
- 宿舍扣费相关服务：`service/admin/AdminManagementService.java`

以奖励兑换为例，实现步骤大致如下：

1. 校验奖励是否存在。
2. 校验奖励是否启用、库存是否充足。
3. 校验学生当前积分是否足够。
4. 校验通过后统一扣减积分。
5. 同步扣减奖励库存。
6. 写入奖励兑换记录。
7. 返回更新后的积分和库存结果。

以支付订单为例：

1. 创建订单记录。
2. 生成订单编号和支付信息。
3. 支付成功后进入统一业务处理流程。
4. 更新宿舍余额。
5. 写入账单流水。
6. 触发后续低碳积分相关计算。

### 3.3 答辩可用表述

对于多表同时更新的业务，我把关键操作统一收敛到后端业务层，采用“先校验、再统一更新”的方式处理，保证余额、积分、库存和记录之间的数据一致性。

## 4. 难点四：双角色权限边界如何实现

### 4.1 难点说明

系统同时存在三类访问场景：

- 学生端访问
- 管理员端访问
- 部分公开查询访问

如果只靠前端隐藏页面，是无法真正保证安全性的，因此权限控制必须同时在前后端实现。

### 4.2 实现方式

#### 前端实现

前端通过统一路由守卫控制访问：

- 路由文件：`low-carbon-dormitory-vue/src/router/router.ts`

主要做法：

- 使用 `requiresStudentAuth` 区分学生端受保护页面。
- 使用 `requiresAdminAuth` 区分管理员端受保护页面。
- 学生和管理员登录态分别存在独立 Store 中：
  - `src/stores/student-token.ts`
  - `src/stores/admin-token.ts`

#### 后端实现

后端通过 Token 校验和拦截器控制真实身份：

- 拦截器：`config/AuthTokenInterceptor.java`
- Web 配置：`config/WebCorsConfig.java`
- Token 服务：`service/auth/TokenService.java`

后端实现逻辑包括：

1. 从请求头中读取 `Authorization`。
2. 校验 Bearer Token 的合法性。
3. 解析用户角色信息。
4. 判断当前接口是否允许该角色访问。
5. 将身份信息写入请求上下文，供后续业务层使用。

### 4.3 答辩可用表述

本项目的权限控制不是只依赖前端页面跳转，而是采用“前端路由守卫 + 后端 Token 拦截”的双层机制，前端负责交互层限制，后端负责真实身份校验。

## 5. 难点五：前端页面多、路由复杂如何组织

### 5.1 难点说明

本项目前端页面不只包含学生端，还包含管理员端、移动端嵌入式页面，以及餐厅管理子模块。  
如果不提前做结构化设计，后期页面一多，路由和组件之间就会非常混乱。

### 5.2 实现方式

前端采取“按角色拆页面、按业务拆接口、按模块拆目录”的方式组织工程。

关键结构如下：

- 学生端页面：`src/router/student-router/`
- 管理员端页面：`src/router/manager-router/`
- 餐厅子模块：`src/modules/restaurant/`
- 公共组件：`src/components/`
- 接口模块：`src/api/modules/`
- 统一路由：`src/router/router.ts`

导航组件也分角色独立实现：

- 学生导航：`components/student-global-nav.vue`
- 管理员导航：`components/admin-global-nav.vue`

同时，项目还将不同 API 按业务拆分为：

- `student.ts`
- `admin.ts`
- `dashboard.ts`
- `reward.ts`
- `low-carbon-rule.ts`

### 5.3 答辩可用表述

面对前端页面数量多、角色多、模块多的问题，我采用模块化目录结构来组织项目，通过统一路由管理、分角色页面拆分和按业务封装接口，保证了前端工程的可维护性。

## 6. 难点六：系统扩展性如何考虑

### 6.1 难点说明

项目当前的核心是宿舍低碳管理，但系统后续并不一定只停留在宿舍业务，还可能扩展到餐厅、校园节能等绿色治理场景。  
因此，项目设计时就不能只考虑当前页面能不能跑通，还要考虑未来能不能扩展。

### 6.2 实现方式

项目在管理员端已经集成了餐厅模块相关路由，例如：

- `/manager/restaurant/summary`
- `/manager/restaurant/student/list`
- `/manager/restaurant/student/meal/*`

这说明项目在结构上已经具备模块扩展能力，做法主要有：

1. 前端按模块独立目录管理。
2. 路由按业务域分段组织。
3. 后端按控制器、服务、实体分层设计。
4. 通过统一文档、统一发布目录支撑持续迭代。

### 6.3 答辩可用表述

为了保证项目不是一次性 Demo，我在架构设计上保留了模块扩展空间，当前管理员端已经接入餐厅子模块，后续可以继续向校园绿色治理平台演进。

## 7. 总结版表述

项目最主要的难点有六个：

1. 如何把水电数据抽象成低碳积分规则。
2. 如何处理宿舍、水电、积分、奖励之间的多模块联动。
3. 如何保证充值、扣费、兑换等操作的数据一致性。
4. 如何处理学生端和管理员端的权限边界。
5. 如何组织复杂的前端页面和路由结构。
6. 如何让系统具备后续扩展能力。

对应的实现思路是：

- 规则抽象放到后端配置服务。
- 多模块联动放到 Service 层聚合。
- 高一致性业务统一由后端业务层处理。
- 权限通过前端路由守卫和后端 Token 拦截双层控制。
- 前端通过模块化目录和按业务拆分接口组织工程。
- 整体结构预留多场景扩展能力。

## 8. 一段可直接背诵的答辩话术

本项目的难点主要不在页面本身，而在业务抽象和工程实现上。首先，系统需要把宿舍水电消费数据转化为低碳积分和排名，因此我将低碳计算逻辑抽象成后端可配置规则，而不是写死在前端。其次，项目中的水电、积分、奖励和账单之间存在较强联动，所以我采用实体拆分和 Service 聚合的方式集中处理复杂业务。再次，在充值、扣费、奖励兑换这些场景中，涉及多表更新，我通过后端统一业务流程保证数据一致性。在权限方面，我没有只依赖前端页面控制，而是结合前端路由守卫和后端 Token 拦截实现双层校验。最后，考虑到系统后续还要扩展到更多校园场景，我在前后端结构上都采用模块化设计，保证了项目的可维护性和扩展性。
